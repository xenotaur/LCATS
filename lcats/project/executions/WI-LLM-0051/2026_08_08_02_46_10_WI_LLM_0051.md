# Result

Fixed a pre-existing bug in `WI-LLM-0051.md`'s own frontmatter before
implementation could even start: comments interleaved inside the
`artifacts_expected` YAML list are valid YAML (PyYAML parses them fine)
but broke lrh's own hand-rolled frontmatter parser
(`lrh.control.parser.parse_markdown_text`), making
`lrh work-items readiness WI-LLM-0051` fail with "work item not found"
even though `lrh validate` reported 0 errors - only `lrh work-items
validate` caught it as `malformed-frontmatter`. Removed the interleaved
comments (their content was already present in the Scope section prose,
so nothing was lost). Flagged the identical bug in `WI-LLM-0056.md` as a
separate background follow-up task rather than fixing it in this PR
(out of scope).

Ran 3 more real, live Ollama benchmark calls via `common/harness.py`'s
`run_segmentation()`: a 3rd attempt at the identical `(qwen3:8b,
five_orange_pips)` config `WI-LLM-0050` used, a different story
(`corpora/sherlock/engineers_thumb`) on the same model, and a different
model (`qwen3:30b-a3b`) on the same story. All 3 failed identically
(`finish_reason='stop'`, no tool call, despite schema-shaped free-text
content) - **5/5 total segmentation attempts failed** across 2 models
and 2 stories, including 3 independent samples at the identical config.

**Verdict: reproduced at 100% frequency, not intermittent.** This is
strong evidence the gap is a structural limitation of Ollama's
OpenAI-compatible `tool_choice` against `SEGMENT_TOOL_SCHEMA`'s specific
shape (large, nested), not a per-model reliability issue -
`run_entity_extraction()`'s smaller/flatter schema has never shown this
failure across any candidate tested in this proposal's history.

**Retry path: considered per the WI's own scope, explicitly rejected.**
The 3 repeated attempts at the identical config are themselves empirical
evidence against a retry helping - if `temperature=0.6` resampling were
enough to sometimes dodge the failure, at least one of the 3 identical-
config attempts should plausibly have differed; none did. Adding a
retry would double latency/cost for no observed chance of success. No
code changes made to `common/harness.py` or either backend as a result
- documented as the WI's own anticipated "explicit, reasoned decision
not to add one" outcome.

Documented the full verdict in `PROP-ERW-LOCAL-MODEL-EVALUATION`'s new
"Decision 3 update (2026-08-08, `tool_choice` reliability investigation,
`WI-LLM-0051`)" section, updated the Implementation Plan and Open

investigation" section to `ollama_qwen3_8b/README.md`. Only the 3rd
