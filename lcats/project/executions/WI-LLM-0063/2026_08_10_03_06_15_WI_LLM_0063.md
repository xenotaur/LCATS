# Result

- **Genre detection: 3/3 success** (`benchmark_genre.py`,
  `results_genre_run{1,2,3}.json`), all correctly detected `mystery`.
  Latencies 40.5s/8.3s/13.5s - the drop after run 1 is plausibly Ollama's
  model-load warmup, not a per-call cost.
- **Entity extraction: 3/3 success** (`benchmark.py`, added a 3rd run
  alongside `WI-LLM-0056`'s 2 pre-existing: `results_run{1,2,3}.json`).
  The added run revealed real, substantial variance the 2-run sample
  hadn't shown: latency 35-170s (~4.5x spread), entity count 12-34 (~3x
  spread). `success` never flipped to failure, but a single run's entity
  count should not be treated as representative without a future
  precision/recall check (out of this tranche's Non-Goals).
- **Segmentation: 0/3 - a genuinely new failure mode**
  (`benchmark_segmentation.py`, `results_segmentation_run{1,2,3}.json`).
  `run_segmentation()`'s existing `retry_with_reminder=True` default (from
  `WI-LLM-0051`, unchanged by this diff) fired on all 3 baseline
  `no_tool_call` failures, and the retry did get the tool actually
  invoked each time - unlike `gemma4:12b`/`deepseek-r1:14b`, where the
  reminder sometimes still fails to produce a call at all. But the
  resulting segment then failed the segmenter's own downstream alignment
  validation (`anchor text not found in story text`) in all 3 runs. This
  is distinct from both mechanisms `WI-LLM-0062` characterized (silent
  ignore, active filter rejection) - a failure in answer *quality* after
  a successful tool call, not in tool invocation itself.
