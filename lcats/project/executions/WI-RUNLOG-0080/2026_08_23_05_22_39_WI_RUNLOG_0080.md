# Result

`_run_stories()` now takes a `log: run_log.RunLog` parameter and emits
one event per story (`story_completed`, `story_unexpected_error`, or
`run_aborted_fatal`) after each story's outcome resolves. `main()` wraps
both the `_run_stories()` call and the `pilot_stories.jsonl`/
`pilot_usage.jsonl` write block in a single `RunLog` scope (log path
`<output_dir>/pilot_run_log.jsonl`, via the same `checkpoint.CheckpointRoots`
object `main()` already builds), so a failure during those writes also
produces `run_aborted_unexpected`, never a false `run_end` implying
success — mirroring the review finding fixed for WI-RUNLOG-0079.
`pilot_summary.json`, written after the scope closes, is explicitly out
of scope per the WI. No changes to per-item checkpointing or to the
`pilot_stories.jsonl`/`pilot_usage.jsonl` output format.

Added 3 tests to `run_pilot_test.py`: event ordering on a clean run,
partial-log survival on a simulated `FatalPilotError` mid-run (using
`--story-list` for deterministic story ordering, since the full
stratified-sample path's genre-detect scan order isn't deterministic by
filename), and write-failure producing `run_aborted_unexpected` rather
than `run_end` (a selective `Path.open` patch targeting only
`pilot_stories.jsonl`, since a blanket patch would also break
`Path.read_text()`-based story reads inside `_run_stories()`).

Ran a diff-mode `/lrh-self-review` pass before pushing (Step 7.5) — clean,
no blocking findings. One non-blocking observation (a fatal abort's log
contains both `run_aborted_fatal` and a trailing automatic `run_end`,
since `FatalPilotError` is caught inside `_run_stories()` rather than
propagating out of the `with` block) was independently re-verified
directly against `run_log.py:193-194` and confirmed accurate but not a
defect — no acceptance criterion requires suppressing it, and (unlike
WI-RUNLOG-0079) this WI doesn't require a rich `run_end` payload, so no
manual override was needed.
