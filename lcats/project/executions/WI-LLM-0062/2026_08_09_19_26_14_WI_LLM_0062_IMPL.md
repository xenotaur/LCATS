# Summary

Implement WI-LLM-0062 via `/lrh-execute` (which inlines `/lrh-implement`
then `/lrh-land`) - investigate both `tool_choice` failure mechanisms
found in `WI-LLM-0056`'s tranche 1: mechanism (a) silent-ignore
(`ollama_gemma4_12b`, `ollama_deepseek_r1_14b`) and mechanism (b) active
filter rejection (`gemini_flash`), independently.

# Result

**Mechanism (a):** added a new opt-in
`run_entity_extraction(..., retry_with_reminder: bool = False)`
parameter to `common/harness.py`, refactored into
`_run_entity_extraction_once()` + a retry wrapper mirroring
`run_segmentation()`'s existing `WI-LLM-0051` mechanism exactly
(retargeted at `extract_entities`'s actual tool name via a new
`_ENTITY_RETRY_REMINDER` constant). Defaults to `False`, preserving
every existing candidate's behavior unchanged - verified by grepping
all `run_entity_extraction(` call sites across every `benchmark.py`,
none pass `retry_with_reminder=True`.

- `ollama_gemma4_12b`: a real methodological confound surfaced first and
  had to be corrected before the actual question could be tested - the
  harness's default `max_tokens=8192` genuinely wasn't enough for this
  candidate's tool-call output (3/3 runs hit `truncated_output`, meaning
  the retry path never even fired, since only `error_type="no_tool_call"`
  triggers it). Raised to 16384 (matching
  `DEFAULT_SEGMENTATION_MAX_TOKENS`'s precedent). At the corrected
  setting, 4 real runs: 1 baseline success (no retry needed), 1 baseline
  call that timed out outright (a third distinct failure mode, not
  addressable by the reminder), 1 baseline-fail-then-retry-succeeded (17
  entities), 1 baseline-fail-then-retry-timed-out. **1 of 2 applicable
  retries succeeded** - a real, partial mitigation effect, consistent with
  segmentation's own 40% finding.
- `ollama_deepseek_r1_14b`: 3 real runs, all baseline `no_tool_call`, all
  3 reminder-retries also failed (0/3). Also tested `temperature=0.6`
  alone (the other untested variable `WI-LLM-0056` flagged, since
  `ollama show deepseek-r1:14b --parameters` reports no
  candidate-specific temperature override) - also failed. A more robust,
  harder-to-mitigate instance of the silent-ignore mechanism than
  `gemma4:12b` - a real, negative, complete finding.

**Second self-caught process error:** the automatic first-push review on
this PR (Codex) correctly caught that the retry wrapper for both
`run_segmentation()` (pre-existing, `WI-LLM-0051`) and the new
`run_entity_extraction()` retry path returned only the *retry* call's own
`latency_seconds`/`input_tokens`/`output_tokens`, silently discarding the
failed baseline attempt's real resource use - every reminder-mitigated
benchmark was underreporting total cost. Fixed in `run_entity_extraction()`
(the code this diff actually introduces; `run_segmentation()`'s identical
pre-existing gap is out of scope, flagged separately). Regenerated every
affected committed result (`ollama_deepseek_r1_14b`'s all 3 runs;
`ollama_gemma4_12b`'s 2 retry-attempted runs) - one `gemma4:12b` result
could not be regenerated with an identical qualitative outcome (a fresh
attempt at the same config timed out on the retry rather than succeeding
again), so that older, pre-fix "retry succeeded" result was kept as a real,
valid qualitative data point with its resource numbers explicitly flagged
as a known undercount, rather than silently discarding a genuine
observation just because a later, different run happened not to reproduce
it identically.

**Mechanism (b):** tested the original "schema complexity triggers
Gemini's `MALFORMED_FUNCTION_CALL` filter" hypothesis directly, via a
new committed diagnostic script (`gemini_flash/benchmark_minimal_schema.py`,
a genuinely minimal flat single-field schema) and a second new script
re-running the real, unmodified `ENTITY_TOOL_SCHEMA` at higher
`max_tokens` (`gemini_flash/benchmark_full_schema_32k.py`). Minimal
schema: 3/3 success at `max_tokens=2048`. Full schema at increasing
budgets: 8192/16384 both failed with `truncated_output` (not even
reproducing the original `MALFORMED_FUNCTION_CALL` signal); 32000
succeeded 3/3. **Verdict: the original schema-complexity hypothesis is
not supported** - the same schema that "systemically" failed in
`WI-LLM-0056` succeeds reliably once given enough token headroom. The
real constraint appears to be token budget (likely Gemini 3.x's
"thinking"/reasoning consumption sharing the same budget as the visible
completion), not schema shape.
