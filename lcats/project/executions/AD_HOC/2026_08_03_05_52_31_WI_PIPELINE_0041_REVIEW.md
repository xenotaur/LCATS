# Summary

Address PR #217's review round on `run_pilot.py` (5 comments from a
combination of Copilot and Codex, all confirmed valid on triage): missing
checkpoint-payload validation at 2 remaining read sites, incomplete
checkpoint fingerprints (missing story-body/NLP-backend inputs),
unconditional "success" outcome on checkpoint writes regardless of
extraction errors, and usage-data loss on a fatal abort from the
cross-segment stage.

# Result

- **Payload validation (Copilot)**: `run_story()`'s `cached_erw.data` and
  `cached_cross.data` reads are now guarded by `_is_valid_cache_payload`
  (the same helper already applied at the `genre_detect`/`segment` sites
  in the prior round), with required-key sets matching what each stage's
  data is actually used for downstream (`_erw_keys` includes
  `segment_ids_with_events` since `_apply_cross_segment_relations` reads
  it from a cached `extraction_result`; `_cross_keys` is just
  `("story", "usage")`).
- **Fingerprint completeness (Codex P1)**: `genre_detect`'s and
  `segment`'s fingerprints now hash the actual input text (the raw file
  read for genre-detect, the coerced `body` for segmentation) via
  `_stage_fingerprint(..., upstream=...)` instead of the bare
  `_base_fingerprint` - correcting a story's content now invalidates both
  caches even under an unchanged model/backend. `erw_extract`'s
  fingerprint now folds in `nlp_backend_name` alongside `segments`
  (previously omitted, even though the NLP surface-feature backend choice
  affects `process_segment()`'s output).
- **Outcome determination (Codex P1)**: `erw_extract`'s checkpoint write
  now checks `_has_extraction_errors(extraction_result)` (reusing the
  existing helper, since `extraction_result` already has the `segments`/
  `story` shape it expects) and writes `outcome="failure"` when errors are
  present, instead of always `"success"`. `cross_segment_relation`'s write
  does the equivalent check against `cross_segment_result["story"]`'s own
  `extraction_errors`. Either way, `checkpoint.read_checkpoint`'s
  `done=(outcome == "success")` rule means a resumed run now retries a
  story whose extraction genuinely failed, rather than treating it as
  permanently done.
- **Usage preservation on fatal abort (Codex P2)**: `_apply_cross_segment_relations`
  gained an `upstream_usage` parameter; its own `_check_fatal` call (fired
  when the story-relation LLM call itself hits an account-level error) now
  reports `(upstream_usage or []) + [current stage's own usage]`, so
  erw_extract's already-accumulated usage rows are preserved in the abort's
  cost/latency record instead of silently dropped. `run_story()` and the
  backward-compatible `_run_erw_pipeline()` wrapper both now pass
  `extraction_result["usage"]` through.
- Also fixed (already applied before this round's own record was created,
  during the same review-response work): `main()` now resolves
  `checkpoint.resolve_roots()` before creating `--output`, so a rejected
  path can no longer mutate the protected corpus tree first (Codex P2).
- New test: `TestErwExtractFailureIsNotCheckpointedAsDone` (patches
  `_run_erw_extraction` to return a result carrying `extraction_errors`,
  confirms the written checkpoint's `outcome` is `"failure"`, not
  `"success"`).
- Updated `TestCheckpointedResumability`'s KeyboardInterrupt test to
  reconstruct the segment checkpoint's fingerprint via
  `_stage_fingerprint(..., upstream=body)` instead of the now-removed bare
  `_base_fingerprint` call, matching the fingerprint-completeness fix
  above.
