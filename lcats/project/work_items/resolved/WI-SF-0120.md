# Work Item: WI-SF-0120

## Summary

Make each model call's tool-forcing request observable by persisting a small, secret-free record of what the runner sent, so a canary can show whether `strict`, `tool_choice` and the closed schema were part of the request.

## Problem / Context

The WI-SF-0116 report (`experimental/science_fiction_analysis_trial/heinlein_canary_report_v2.md`) could not settle whether `strict` reached Ollama: the runner persists the raw response but not the request, so forwarding is unobservable from the results. `openai_backend.py` builds the request (the tools block with `strict` and the forced `tool_choice`), and WI-SF-0114 added key checks and a text fallback, so knowing whether a tool call was forced and constrained is the missing evidence for deciding how much to rely on schema enforcement (see the strict-schema forwarding memory note).

### Duplication search
- In-repo: no existing request logging in the runner; the backend builds but does not record the request.
- Sibling repos: none identified.
- External libraries: none identified.
- Recommendation: proceed.

## Scope

- The runner's model-stage call path (`_run_model_stage`) and its persisted artifacts, an optional request-capture hook on the LLM backend interface and `OpenAIBackend`, and the canary runbook's list of committed artifacts, with tests.
- Only the fields about tool forcing; the prompt text and story content stay out because the checkpoint fingerprint already covers them.

## Required Changes

1. Persist, per stage call and next to the raw response, the tool name, the tool schema as sent (including the `strict` value), the `tool_choice` block, the model, temperature and max tokens, and whether the call went through the tool path or the text fallback.
2. Make the backend request-capture API an explicit deliverable: an optional, off-by-default, out-of-band capture: a per-call recorder (callback or recorder argument) that `OpenAIBackend` invokes with the provider request as actually built, before the network call, so a request is recorded even when `complete()` then raises (`TruncatedResponseError` at `openai_backend.py:77`, `NoToolCallError` at `:104`, or a provider error); a returned value would give no record for failed attempts. `LLMBackend` is a `@runtime_checkable` Protocol, so the hook must not be a new required method: make it an optional keyword or a separate optional Protocol discovered with `getattr`, so the Anthropic backend, `FakeBackend` and test doubles keep conforming. The runner's `--backend fake` smoke uses `DeterministicSpikeBackend` (`run_worldcon_spike.py:198`), not `src/lcats/llm/fake_backend.py`, and neither sees the runner-level `tool` argument, so neither can stand in for the provider transformation (`tools[].function.parameters`, `strict`, `tool_choice`); test the real record with a stubbed OpenAI client and keep the fake smoke for runner artifact plumbing only. Existing callers and the Anthropic backend must be unaffected.
3. Keep fingerprints, checkpoint reuse and resume validation unchanged, and prove it with tests; the new files must not be part of any fingerprint or reuse check.
4. Record the request once per attempt, because `_run_model_stage` retries truncation and transient failures with a changed `max_tokens` and persists failed attempts separately: each record carries its attempt number and effective `max_tokens` and is stored beside that attempt's raw or error artifact. Add no-cost tests: a stubbed-client test of the provider request, a smoke run with `DeterministicSpikeBackend` whose files contain no absolute paths or credentials and omit the system prompt and story text, a truncation-retry case and a terminal-failure case (both need a stub backend that raises, since `DeterministicSpikeBackend` never does), and a resume that still reuses checkpoints.
5. Update the canary runbook's list of committed artifacts to mention the new files.

## Non-Goals

- Do not run live model trials, change prompt versions, change fingerprints, or log the system prompt, story text or any credential.
- Do not claim anything about what Ollama does with the fields; this item only makes the question answerable.

## Acceptance Criteria

- The backend exposes an optional, off-by-default request-capture hook, and a test with a stubbed OpenAI client shows that the persisted record matches the provider request `OpenAIBackend` actually builds (tools block with the schema and `strict` value, and the forced `tool_choice`)
- A smoke run writes a request record for each attempt of each model stage call next to its raw response, including retries with a changed `max_tokens` and a terminal failure, each tagged with its attempt number and effective `max_tokens`
- The persisted request files contain no credentials, no absolute paths, and neither the system prompt nor the story text
- Stage fingerprints, checkpoint reuse and the existing Heinlein, Knight and Suvin tests are unchanged and pass
- `lrh validate` reports 0 errors
