# Work Item: WI-SF-0121

## Summary

Add a private-server procedure and preflight to the Heinlein canary runbook so a local canary does not share an Ollama server with another client or lose time to machine sleep.

## Problem / Context

The WI-SF-0116 rerun (`experimental/science_fiction_analysis_trial/heinlein_canary_report_v2.md`) shared its Ollama server with another session's agent, which swapped models in the same server, and the machine slept for about 90 minutes during trial 3, so one stage showed 5710 s of wall-clock against 914 s of runner latency. Both effects obscure latency and can disturb a stochastic run, and the runbook says nothing about either.

### Duplication search
- In-repo: the runbook and `docs/how-to/local-openai-endpoint.md` describe a single local server but not isolation or sleep.
- Sibling repos: none identified.
- External libraries: none identified.
- Recommendation: proceed with a runbook change; extend the how-to only if a shared step belongs there.

### Demand search
- Work items: none found; the only demand is the WI-SF-0116 report and its closeout note.
- Proposals: none found.
- Backlog: no matching entry found.
- Recommendation: no action; link to WS-KNIGHT-NOVUM-ANALYSIS.

## Scope

- Documentation changes to the canary runbook, and the how-to if a step belongs there.
- No code, no automation of server start-up, and no live run.

## Required Changes

1. Document starting a dedicated server on a non-default loopback port with the environment settings used for WI-SF-0116, pointing the runner at that port. Treat `ollama ps` as necessary but not sufficient: it lists loaded models, not client identity or completed requests, and the WI-SF-0116 report's before and after rows were identical while the server log showed intervening `gemma4:12b` swaps. The isolation check is the server log, reviewed after the run for any model load or request other than the target model's; state in the runbook that client identity cannot be proven, so the private port and the `OLLAMA_HOST` setting are the actual control.
2. Document keeping the machine awake for long runs and, after any stage that took much longer than the measured runner latency, checking the system log for a sleep interval before diagnosing the server.
3. Record in the runbook that persisted results from a run on a shared server are not comparable on latency, and that its commands use the v1 roots unless the v2-style roots are substituted.
4. Check the documented steps against the WI-SF-0116 report's setup section so they match what was done.

## Non-Goals

- Do not change the runner or the manifest, run live trials, or add automation.
- Do not claim the private server removes run-to-run variance in the model's output.

## Acceptance Criteria

- The canary runbook has a numbered private-server procedure that names a non-default loopback port, the `OLLAMA_HOST` and `OLLAMA_NO_CLOUD` settings used, and how to check the server log, after the run, for any model load or request other than the target model; `ollama ps` alone is not accepted as proof
- The runbook has a keep-awake step for long runs and a post-run check of the system log for sleep intervals, to compare against any stage that took much longer than the measured runner latency
- The runbook states that its v1-root commands append to the results of the first canary and points to the v2-style roots
- `lrh validate` reports 0 errors

## Risk Notes

- The procedure depends on the host (macOS keep-awake, log commands); state them as examples, not requirements.
- Another session may legitimately need the default server; the runbook must not tell an operator to stop it.
