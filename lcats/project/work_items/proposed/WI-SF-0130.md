# Work Item: WI-SF-0130

## Summary

Show the date-aware profile in reports and document the profile category names where a reader will see them.

## Problem / Context

The profile is the output the owner will read: evergreen, overtaken, plausible when written (today undetermined), plausible only in retrospect, fails when written, undetermined, and not applicable. Owner decision Q3: the R7 names are adopted, reviewed before implementation, and documented in user documentation and in code comments. WI-SF-0126 puts the names in code comments; this item puts them in the documentation and in the rendered report so the same words appear everywhere. The proposal's Compatibility list names `rendering.py` (a view and columns for the new profile) and the three documents that enumerate the Heinlein stage.

### Duplication search
- In-repo: the existing Heinlein view is the pattern. Recommendation: proceed.

### Demand search
- The proposal's Implementation Plan item 5. Recommendation: no action.

## Scope

- A rendering view and columns, user-facing documentation of the names, and updates to the three documents.

## Required Changes

1. Add the view and columns to `rendering.py`, omitted when the record is absent.
2. Write the category table (name, meaning, inputs) in the documentation and cross-check it against the code comments.
3. Update the README, definitions and runbook to describe the new opt-in stage.
4. Add rendering tests.

## Non-Goals

- No change to the derivation rules, contract or stage, and no live run.

## Acceptance Criteria

- The rendering shows the profile category, the as-written and today statuses, the conditions of any ambiguous result, the speculative-premises flag, the calendar-expired flags and the per-premise relations, as a view with columns beside the existing Heinlein view, and the output is omitted for sidecars without the new record
- The R7 profile category names are defined in user-facing documentation (a table of the names with plain meanings and the P1 and P3 inputs) and the documentation matches the code comments added by WI-SF-0126
- The documents that enumerate the Heinlein stage (`science_fiction_analysis_trial/README.md`, `definitions.md`, `heinlein_canary_runbook.md`) describe the new stage and state that it is opt-in and the existing record is unchanged
- Rendering tests cover a record with every category, a record with ambiguous results, and a sidecar without the record, and `lrh validate` reports 0 errors

## Validation

- `PYTHONPATH=src scripts/test`
- `scripts/lint`
- `lrh validate`
- `git diff --check`

## Dependencies / Order

Depends on `WI-SF-0126` (the record) and `WI-SF-0127` (the stage, for accurate documentation). Not required by WI-SF-0131 but should land before results are reported to the owner.

## Risk Notes

- Documentation of the names can drift from the code table; the acceptance criterion requires the two to match, and a test or review check should compare them.
- A report that shows a profile without the premises behind it invites over-reading; the view includes the per-premise relations and conditions for that reason.
