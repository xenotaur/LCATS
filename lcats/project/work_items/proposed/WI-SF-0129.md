# Work Item: WI-SF-0129

## Summary

Add a small curated table of facts whose standing changed, and a matcher that audits the date-aware stage's model-asserted claims against it.

## Problem / Context

The date-aware stage depends on the model recalling when a fact changed, and a mistaken recall would make the readings look more certain than they are. The proposal makes the stage name each fact and date and mark it `model_asserted`, with a curated table as the audit layer in a later phase (R10 and Open Question 6). The six-story trial found only one date-sensitive story, A Case of Sunburn, whose Mars premises flip at Mariner 4 (15 July 1965); the table starts with such known cases. Owner decision: the table audits the model; it never overrides the owner or the record without being reported.

### Duplication search
- In-repo: no fact table exists. Recommendation: proceed.

### Demand search
- The proposal's Implementation Plan item 4. Recommendation: no action.

## Scope

- The seed data file, the matcher, tests, and a short note on how to add an entry.

## Required Changes

1. Define the entry format (claim, standing periods with closed year or year-month boundaries, source) and seed at least the Mars, Venus and Mercury cases, opening each cited source.
2. Implement the matcher: `table_confirmed` on agreement, a reported disagreement otherwise, no effect on unmatched claims.
3. Add tests for agreement, disagreement and no match, and a note on adding entries.

## Non-Goals

- No attempt to cover the corpus; the table is a seed and an audit aid, not an authority.
- No change to derived statuses and no automatic correction of the model.

## Acceptance Criteria

- A small data file lists known cases of a fact whose standing changed (at least Mars after Mariner 4 on 15 July 1965, Venus surface conditions, and Mercury rotation), each with the claim, the standing periods with year or year-month boundaries, and a cited source that was actually opened
- A matcher marks a model-asserted premise `table_confirmed` when it matches a table entry and its timeline agrees, and flags a disagreement without overriding the model, and the basis vocabulary (`model_asserted`, `table_confirmed`, `owner_supplied`) is the one defined in the proposal
- The table never silently changes a derived status; a disagreement is reported in the record and the unit tests cover agreement, disagreement and no match
- Every entry has a source that was opened and read, unopened sources are labelled unconfirmed, and `lrh validate` reports 0 errors

## Validation

## Dependencies / Order

Depends on `WI-SF-0127` (the stage produces the claims the matcher audits). Blocks WI-SF-0131.

## Risk Notes

- Matching a free-text claim to a table entry is fuzzy; a false match would mark a wrong claim `table_confirmed`. The matcher should key on a stable claim identifier supplied by the stage, not on string similarity alone.
- Citing a source that was not opened repeats the trial's weakness; every entry must be read.
