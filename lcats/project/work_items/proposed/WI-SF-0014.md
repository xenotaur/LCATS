# Work Item: WI-SF-0014

## Summary

Add typed retry handling, accurate usage accounting, and checkpoint-aware resume behavior so isolated story failures do not force a 146-story Worldcon run to repeat successful work or stop prematurely.

## Problem / Context

The current runner executes selected stories but does not yet implement stage-specific retries, a `max_failures` stop condition, or skipping of valid completed stages. Truncation exceptions carry provider usage that can be lost in story-level accounting, and a full run needs a different operational policy from a short canary. This item adds bounded failure-aware retries and the missing failure guardrail while making the full run resumable and safe to continue through isolated failures.

The work builds on `WI-SF-0013`'s explicit model-boundary findings and existing atomic checkpoint utilities. It must preserve experiment-local output roots and must not turn retries into a way to manufacture favorable results.

- Sibling repos: None identified.

- Proposals: The adopted Knight/Novum proposal requires per-stage checkpoint reuse and explicit partial success.
- Backlog: Existing pipeline-checkpointing and structured-output reliability artifacts provide related requirements.
- Recommendation: Link and extend the existing demand; do not close or rewrite the earlier items.

## Scope

- Classify stage outcomes into retryable, repairable, non-retryable, and systemic failures.
- Add one truncation retry with a higher stage-specific token limit and one transient provider/network retry.
- Preserve per-attempt raw output, usage, latency, and failure records.
- Add story/stage fingerprint checks and resumable full-run orchestration.
- Keep canary stop behavior separate from full-run continuation behavior.

## Required Changes

1. Add typed failure classification for truncation, transient provider/network failure, content filtering, structural failure, semantic validation failure, and unknown failure.
2. Retry truncation once with an increased evidence-stage limit, preserving both attempts and their usage.
3. Retry transient provider/network failures once with bounded exponential backoff and jitter; retry only at the model-stage boundary.
4. Do not retry content-filter failures or deterministic validation failures automatically; quarantine them with actionable diagnostics.
5. Add one bounded structural-repair attempt only for findings classified as repairable by `WI-SF-0013`.
6. Transfer token usage from backend exceptions such as `TruncatedResponseError` into story and run totals.
7. Define a stage checkpoint key from story hash, stage, prompt hash, schema hash, model/backend, generation parameters, and effective input fingerprint.
8. Reuse only validated completed stage artifacts whose checkpoint key matches; reject stale hashes and stale configurations.
9. Resume incomplete stories from the first missing or invalid stage without repeating valid completed stages.
10. Add configurable `max_failures=3` for canary/debug modes; make full-run failure continuation and systemic-failure stop conditions explicit manifest settings rather than implicit constants.
11. Add tests for retry classification, attempt persistence, exception usage accounting, interruption, resume, stale checkpoints, isolated failures, and systemic stop conditions.

## Non-Goals

- Do not run the 146-story sample or any paid model calls in this item.
- Do not retry content-filter or deterministic semantic-validation failures.
- Do not add unlimited retries, cross-layer retry loops, or concurrency changes unrelated to this scope.
- Do not modify corpus promotion, production annotation commands, or corpus sidecars.
- Do not define final Phase 2 or Phase 3 quality thresholds.

## Acceptance Criteria

- Truncation and transient failures each have one bounded, separately logged retry path; content-filter and deterministic validation failures do not retry.
- Every attempt has persisted raw/failure/usage information, including provider usage attached to exceptions.
- A valid checkpoint causes a stage to be skipped only when its story hash and effective input fingerprint match.
- An interrupted run resumes from the first invalid or missing stage without repeating valid completed stages.
- Canary runs stop at three story failures, while full-run continuation and systemic stop policy are explicit and configurable.
- Focused tests and `lrh validate` pass with 0 errors.

## Dependencies / Order

This item follows `WI-SF-0013` so retry and resume decisions operate on explicit stage findings rather than opaque exceptions. It must land before the repeated contract canary and before any 146-story approval package is considered.

## Risk Notes

- Retries can amplify provider load and cost; the policy must remain capped and single-layer, with backoff and a run-level retry budget.
- Resume logic can duplicate or skip work if fingerprints are incomplete; story hash and all effective stage inputs must be part of the checkpoint identity.
- A high full-run failure cap should protect continuity without masking systemic failure; the manifest must distinguish isolated story failures from provider-wide failure.
