# Work Item: WI-SF-0122

## Summary

Make every caller of `_existing_evidence_ids` record the evidence IDs that match nothing in the evidence set instead of discarding them silently, and decide per caller whether a drop fails the stage or only warns.

## Problem / Context

`_existing_evidence_ids` in `run_worldcon_spike.py` keeps only the IDs it can map to evidence records and returns the shorter tuple with no record of what was dropped. Its callers include the Heinlein and Knight normalizers and the Suvin decision builders, so a model that cites invented or mistyped IDs loses them without a trace. The case where every cited ID of a `present` decision is unknown is already rejected: the `HeinleinCriterion`, `KnightCriterion` and `NovumDimensionDecision` validators raise when a `present` decision has no supporting evidence (`src/lcats/analysis/science_fiction/models.py`, lines 219-220, 328-329 and 467-468), and this item keeps that behavior as a regression test, verifying while it audits the callers how each stage runner records the resulting failure. The remaining defect is a dropped ID that leaves no record, either because other valid IDs remain or because the field (counterevidence and other ID lists) does not require evidence. This is the same silent-default pattern WI-SF-0114 removed for Heinlein keys, and WI-SF-0114 listed this function as a follow-up candidate.

## Scope

- `_existing_evidence_ids` and all its callers in the runner, with tests.
- Non-fingerprinted logging of every drop for every caller; any stricter fail-instead-of-warn behavior for Knight and Suvin only after a checkpoint-impact check.

## Required Changes

1. Audit every caller of `_existing_evidence_ids` programmatically (grep the whole repo, not a hand list) and record, per caller, what an unknown ID currently does and what it should do.
2. Return or record the dropped IDs so each drop produces a run-log event naming the stage, the field and the ID, including when the stage then fails validation. In Knight, `_knight_decisions` substitutes the fallback evidence ID only when the model cited nothing; a response that cites only unknown IDs yields an empty tuple and is rejected, so audit that path and cover it in the tests.
3. Keep the existing rejection of a `present` decision left with no resolvable supporting ID, and add a regression test for it per detector; decide and implement whether a dropped ID on a decision that still has resolvable IDs only warns (the default proposed here) or fails.
4. Logging every drop is required for every caller and must not change any fingerprint. For Knight and Suvin, a stricter fail-instead-of-warn behavior is allowed only after checking whether it alters existing checkpoint fingerprints or outputs, and the impact is stated; if that check rules it out, the callers keep warn-only behavior, which still logs every drop.
5. Add no-cost tests for each caller class using fixtures built through the real validator, plus a test that fingerprints are unchanged by the logging.

## Non-Goals

- Do not change the Knight or Suvin prompts, the rubric text, or the evidence builder's existing `type` to `evidence_type` coercion.
- Do not run live trials or edit persisted canary results.

## Acceptance Criteria

- A model response that cites an evidence ID that does not exist in the evidence set leaves a visible record (run-log event or quarantine) instead of being dropped silently
- Unknown IDs that are dropped while other valid IDs remain, or from ID lists that do not require evidence, are recorded for every caller of the function, including Knight and Suvin, through a run-log event that is not part of any fingerprint
- The existing behavior that a `present` decision whose cited IDs all fail to resolve is rejected by the criterion validators is kept and covered by a regression test
- Any change to Knight or Suvin stage outcomes (fail instead of warn) is made only after a recorded checkpoint-impact check, and any change to their fingerprints or outputs is stated
- Existing tests pass unchanged, or each changed expectation is justified in the execution record, and `lrh validate` reports 0 errors
