# Work Item: WI-SF-0114

## Summary

Stop the structured-output stages of the Worldcon spike runner from turning mismatched or empty model output into a successful run. The `WI-SF-0113` canary showed one root cause in two stages: the prompt's wording does not match the tool schema's key names, the model echoes the prompt's words, and the pipeline then continues on empty or defaulted data and reports success. This item fixes the Heinlein stage (mismatched keys fail loudly, a single fenced JSON block in the text fallback is unwrapped through the shared strict helper and recorded in the run log), makes an all-quarantined evidence set a visible evidence-stage failure, aligns the evidence and Heinlein prompt wording with the schema keys, and covers all of it with no-cost tests built from the raw responses the canary captured. Rerunning the live canary is a later step.

## Problem / Context

The `WI-SF-0113` canary (`experimental/science_fiction_analysis_trial/heinlein_canary_report.md`, PR 487) found that `_heinlein_decisions` in `run_worldcon_spike.py` reads the keys `criterion_id`, `status`, and `supporting_evidence_ids`, while `gpt-oss:20b` through Ollama returned `criterion`, `decision` or `decision_state`, and `evidence_ids` in all six raw responses. A missing `criterion_id` makes every criterion default to `not_assessable` with an empty rationale, and the stage still reports `complete` with no quarantine or coercion record. That contradicts the stage's own rule that a bad decision fails validation and is quarantined, not repaired. In the negative-control story the model's raw answers were all `present`, so the stored result hid a likely expectation failure.

Trial 1 also returned a Markdown-fenced JSON block as plain text for one story. `json.loads` rejects it at character 0, which is the designed failure path and worked, but the content was intact.

The canary also showed the same failure one stage earlier, in the shared evidence stage that feeds Knight, Suvin, and Heinlein. For the Vonnegut story the baseline produced 7 usable evidence records, but trials 1 to 3 produced none: the model returned six candidates each time and all six were quarantined as `evidence_type is required` (in the trial 2 raw response the items carry `quotation` and no `type`, where the schema's keys are `quote` and `type`). The evidence prompt says "exact quotation", so the model's key again echoes the prompt's wording. The quarantine was recorded, but the stage reported success and Knight, Suvin, and Heinlein ran on an empty evidence set. This also explains the all-`not_assessable` Heinlein answers and the 0-0 Knight interval for that story, which the merged canary report had called unexplained. The run logs show that in trials 1 to 3 the Vonnegut evidence stage took the runner's text fallback (the forced tool call was not honored) every time, while the baseline used a real tool call; the wrong keys also appeared in real tool calls (for example Bell's Heinlein calls in trials 2 and 3), so the tool-call path is not protected either.

The Heinlein system prompt has the same wording mismatch: it speaks of "decision", "decision states", and "evidence IDs" while the schema keys are `status` and `supporting_evidence_ids`, it names a `rubric_id` key that is not in the schema, it never mentions the required `counterevidence_ids` and `confidence` fields, and it does not say what a dependent criterion should be when its prerequisite is absent.

The tool schema is closed with `strict_tool_schema`, and `openai_backend.py` forwards a `strict` field. The canary showed that Ollama with this model did not constrain the keys. Whether Ollama honors `strict` at all is not confirmed.

The same silent-default pattern exists in `_knight_decisions`, which also substitutes a fallback evidence ID. Knight and Suvin used the correct keys in every canary run, and changing them would alter existing checkpoints, so they are out of scope here.

## Required Changes

1. **Fail loudly on mismatched keys (owner-approved, final).** A response whose criteria cannot be matched to the five `criterion_id` values is quarantined and the story shows `Unavailable`, through the same path as a `JSONDecodeError`. There is no alias map: the keys `criterion`, `decision`, `decision_state`, and `evidence_ids` are not accepted in place of the schema keys, and no response is ever repaired by renaming keys.
2. **Never default silently.** Any missing criterion, or a missing or invalid status, quarantines the stage. `not_assessable` is accepted only when the model actually returned it. A wrongly shaped response never becomes a complete analysis with empty rationales.
3. **Fenced JSON through the shared helper (owner-approved).** The runner already has a text fallback: when a forced tool call is not honored, the backend raises `NoToolCallError`, the runner logs `no_tool_call_json_fallback` and parses the raw text with plain `json.loads` (`run_worldcon_spike.py:824-846`, parse at `:924-926`). Add a keyword-only `strict_fence=False` option to `lcats.utils.extract_json` (`src/lcats/utils/compat.py:131`) and use it in that parse. In strict mode it accepts plain JSON unchanged, or exactly one fenced block labeled `json` with only whitespace outside it and nothing extra on the fence line, and it anchors the closing fence to the end of the text so a JSON string value containing three backticks does not truncate the block. Each unwrap is recorded as a new run-log event next to `no_tool_call_json_fallback`. The unwrapped content then goes through the same key and evidence validation as any other response, so a fenced reply with wrong keys is still quarantined. No field is added to the analysis contract (`models.py:441-452`) or the sidecar. The default behavior of `extract_json`, and therefore of its existing callers (`extraction.py:79`, `llm_extractor.py:584`, `experimental/model_comparison/common/harness.py:839`), does not change. Treat the tolerance as a documented, temporary workaround and keep the prompt's no-Markdown rule.
4. **Investigate key enforcement for local backends without a live call.** From the persisted `WI-SF-0113` raw responses (including which stages took the text fallback and which made real tool calls), the request construction in `openai_backend.py`, and the Ollama documentation, record whether Ollama honors the forwarded `strict` field and closed schema for `gpt-oss:20b`. If the persisted artifacts cannot settle it, record the question as unresolved and defer it to the canary rerun. Do not make a live model call in this item, do not add provider-specific workarounds, and do not edit `openai_backend.py` unless the investigation shows a forwarding bug.
5. **Evidence stage: zero usable evidence is a failure.** When the evidence stage returns candidates and every one is quarantined (zero usable records), record an evidence-stage failure through the existing failure path, with the quarantine reasons in the failure message, instead of reporting success. Downstream stages must not run on that empty evidence set. A model that genuinely returns no candidates for a story keeps its existing behavior; confirm that case in the implementation plan before changing it.
6. **Align the prompts with the schema.** Revise `_evidence_system_prompt` and `_heinlein_system_prompt` so their wording uses the schema's key names (`quote`, `type`, `status`, `supporting_evidence_ids`, and so on), show one literal example of a correctly shaped item, state the defaults (`counterevidence_ids` is an empty array when there is none, `confidence` is a number from 0 to 1), say what a dependent Heinlein criterion should be when its prerequisite is absent, remove the `rubric_id` sentence, and forbid Markdown fences and prose outside the tool call. Do not change the rubric text or any Knight or Suvin prompt.
7. **Checkpoints.** Bump the evidence prompt version and the Heinlein prompt version so checkpoints written under the old prompts or behavior are never reused. Because the evidence prompt is shared, this invalidates earlier checkpoints for all three detectors; that is intended and should be stated in the report. Keep fingerprints of runs that do not use the changed stages unchanged where possible, and record which are not.
8. **No-cost tests.** Use the canary raw responses as fixtures, copied with absolute paths removed: the six Heinlein responses and the Vonnegut evidence responses from the baseline and the three trials. Assert that each fixture passes through the real validator. Cover the decision in item 1, the fenced case, a genuine all-`not_assessable` response, a mixed response, the zero-usable-evidence failure, the evidence responses that previously produced zero records, and the checkpoint changes. Add tests for the `strict_fence` option in `tests/utils_tests/compat_test.py`: default behavior unchanged; a lone fence accepted with CRLF endings and surrounding whitespace; prose before or after, a second block, an unlabeled or other-language fence, extra text on the fence line, and an unclosed fence (truncation) all rejected; a JSON string value containing backticks tolerated. Existing Heinlein, Knight, Suvin, and helper tests stay unchanged and green.
9. **Do not rerun the live canary here.** A rerun is a separate work item or an explicit later `/lrh-execute`.

## Risk Notes

- Failing loudly turns today's silent `complete` results into `Unavailable` or failed ones, which lowers the apparent success rate for models that ignore the schema keys. A zero-evidence story will now fail instead of quietly passing.
- The evidence prompt is shared by all three detectors, so a new evidence prompt version invalidates every earlier checkpoint, and runs with the new prompt are not comparable to earlier ones. A prompt example can also bias the model toward the example's genre.
- Accepting fenced JSON is a robustness tolerance that can harden into an expectation, and it hides that the forced tool call was not honored. It is recorded in the run log only, not in the sidecar, so an auditor with only the sidecar cannot see it. Keep the prompt's no-Markdown rule, count unwraps in the canary report, and treat it as temporary.
- The strict option must anchor the closing fence to the end of the text, or a JSON string containing backticks truncates the block.
- The Knight stage has the same latent pattern; a shared helper would be tempting but would change existing checkpoints and fingerprints.
- Fixtures copied from real responses contain story text and evidence IDs; check their size and content before committing. Confirm that the licensing of the corpus text allows committing excerpts as fixtures.
- `scripts/format` skips `experimental/`, so the runner changes need the pinned black and ruff run directly, and the default environment's tool versions differ from CI's.
