# Work Item: WI-SF-0126

## Summary

Implement the data contract for the date-aware Heinlein record defined in `PROP-LCATS-HEINLEIN-TEMPORAL-REFERENCE`: the premise, standing-timeline and composition-interval records, the Python derivations (rules R2 to R8), the profile categories, and the sidecar plumbing that stores the record as an optional analysis kind. No stage, prompt or model call is added here.

## Problem / Context

The proposal (merged in PR #529 and amended in PR #532) specifies a separate opt-in stage that judges the five Heinlein conditions against the author's world at composition. Every rule that turns a model's premise list into statuses, relations, flags and a profile is deterministic and should exist, validated and tested, before any prompt produces the input. Owner decisions already made and fixed as inputs: the time of a story's setting is never itself a difference; a stipulated departure from history is a `counterfactual_divergence` premise judged on its enabling mechanism; a premise `contested` at composition gives `ambiguous`; the R7 profile names are adopted and must be documented in user documentation and in code comments; the record lives in the same sidecar as `analyses.heinlein_temporal`.

The proposal's Compatibility section lists what a new analysis kind forces: `sidecar.py` (stage names, optional-analysis validation, current-pointer parsing), `models.py` (pointers record, envelope field, `_validate_analyses`, `_iter_analyses`, serialization, and a premise-anchor iteration because the existing evidence iteration assumes records with `.criteria`), and `pipeline.py` (assembly inputs, the optional-when-empty fingerprint, `assemble_sidecar`, current selection). The sidecar schema version is checked for strict equality and hashed into the assembly fingerprint, so it must not be bumped; the Heinlein kind was added the same way.

## Scope

- Contract, validators and derivations for the `heinlein_temporal` record and its sidecar plumbing in `src/lcats/analysis/science_fiction/`.
- Unit tests, including omitted-when-empty and every row of the profile table.

## Required Changes

1. Add the record types: premise (`premise_id`, `kind`, `claim`, anchor, materiality, `novel_at_composition`, `dated_prediction`, standing timeline), composition interval with sources, and the assessment block, following the proposal's Record shapes.
2. Implement the derivations as pure functions: R2 status over an interval (touching boundaries overlap, a missing interval is the widest, `contested` gives `ambiguous`), R3 relation, R4 novelty and `different` (a setting time alone is never novel; a `counterfactual_divergence` is novel and its timeline describes its enabling mechanism), R5 calendar-expired derived from `dated_prediction` and the analysis date, R6 speculative-premises flag, R7 profile category, and R8 `verdict_as_written` with the prerequisite-rule consistency check.
3. Add the sidecar plumbing listed under the proposal's Compatibility for a new analysis kind, omitting the key and pointer when empty, with its own provenance version string, without bumping the schema version.
4. Document the R7 names in code comments next to the derivation table.
5. Add tests beside `heinlein_test.py` and the sidecar tests, including the absent-key assertions modelled on `heinlein_test.py:259-260, 331`.

## Non-Goals

- No stage, prompt, tool schema or model call (WI-SF-0127), no date tooling (WI-SF-0128), no fact table (WI-SF-0129), no rendering or user documentation (WI-SF-0130).
- No change to `heinlein-five-v1`, `HeinleinCriterion`, `HeinleinAnalysis`, the five-criterion prompt or any existing stage fingerprint.

## Acceptance Criteria

- A new optional analysis kind `heinlein_temporal` exists in the same sidecar as `analyses.heinlein_temporal`, omitted when empty, with its own provenance version string, and the sidecar schema version is not bumped
- The premise record (with `kind` of `ordinary` or `counterfactual_divergence`), the standing timeline, the composition interval with per-source basis and confidence, and the derived values (R2 status over an interval, R3 relation, R4 novelty and `different`, R5 calendar-expired and counting, R6 speculative-premises flag, R7 profile category, R8 `verdict_as_written`) are implemented as validators and pure derivations with no model call
- The R7 profile category names are documented in code comments beside the derivation table and the derivation is tested for every row of the table, including `not_applicable` when no speculative premises exist
- Existing sidecars, the `heinlein-five-v1` record, existing stage fingerprints and existing checkpoints load and hash exactly as before, shown by the existing tests passing unchanged
- Omitted-when-empty tests for the new key and pointer exist beside the Heinlein ones, and `lrh validate` reports 0 errors

## Risk Notes

- The premise-based record has no `.criteria`, so the evidence-reference iteration (`models.py` `_iter_criterion_references`, `_iter_evidence_references`) needs its own path; missing it would let anchors go unchecked.
- Adding an optional kind touches the assembly fingerprint; the optional-when-empty rule must keep existing assemblies hashing identically, and this must be shown by a test, not assumed.
- The R7 names are adopted for owner review before implementation; a rename after this lands touches tests, comments and documentation.
